# Architecture

```text
RapidAPI Tennis
     |
     v
normalisation ----> Supabase matches (audit/raw + canonical history)
     |                         |
     |                         v
     |                 point-in-time feature engine
     |                         |
     |                  train + calibration
     |                         |
     |                  model.joblib artifact
     |                         |
     +---- upcoming ----------> prediction refresh
                               |
                               v
                       Supabase predictions
                               |
                               v
                       Azure Functions API
                               |
                  +------------+-------------+
                  |                          |
               Blinq UI                optional web/
```

### Why predictions are precomputed

The 15k/day upstream quota is better spent on batched refreshes than one upstream call for every Blinq page view. Azure serves already-computed probabilities from Supabase, so frontend request volume does not multiply RapidAPI usage.

### Canonical match IDs

Upcoming schedules and historical archives can use different record IDs and different player ordering. TBT computes a canonical ID from tour, date, tournament, round and the **sorted** pair of player IDs. That makes later settlement resilient to the provider's winner-first historical ordering.

### Artifact lifecycle

The model artifact is generated by the scheduled/manual GitHub retrain workflow and deployed together with the Function App. Azure Functions never tries to persist a retrained model in its ephemeral local filesystem.
